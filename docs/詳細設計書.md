### 3.3 vite.config.ts のプロキシ設定

Vite の開発サーバー（デフォルト: `http://localhost:5173`）と Express の API サーバー（デフォルト: `http://localhost:3000`）は **別々のオリジン**になります。フロントエンドから `/api/...` への fetch が CORS エラーになるため、Vite のプロキシ機能を使って解決します。

#### プロキシ設定の役割

```
ブラウザ → Vite 開発サーバー(:5173) → プロキシ転送 → Express(:3000)
         ↑ /api/* へのリクエストを                    ↑ 実際のAPIが応答
           同一オリジン扱いで転送
```

- `/api/` で始まるリクエストのみ Express へ転送します
- ブラウザ側から見ると「同一オリジンのリクエスト」として動作するため、CORS エラーが起きません
- Express が発行する **セッションCookie** もそのままブラウザに届き、ログイン状態が保たれます（`changeOrigin: true` を指定する場合は、Express 側の `express-session` の `cookie.sameSite` 設定と整合させてください）

#### vite.config.ts の例

```typescript
// frontend/vite.config.ts
import { defineConfig } from 'vite';
import react from '@vitejs/plugin-react';

export default defineConfig({
  plugins: [react()],
  server: {
    proxy: {
      // "/api" で始まるリクエストをすべて Express へ転送する
      '/api': {
        target: 'http://localhost:3000',
        changeOrigin: true,
        // Cookie（セッション）をそのまま転送するために必要
        // ※ secure: false にしないと http://localhost では Cookie が送れない場合がある
      },
    },
  },
});
```

#### Cookie（セッション）を保つための注意点

| 項目 | 設定・確認事項 |
|---|---|
| `changeOrigin: true` | プロキシ時のホストヘッダーを書き換える。ほぼ常に必要 |
| Express 側の `cookie.secure` | `false`（開発時は http のため `true` にすると Cookie が送られない） |
| Express 側の `cookie.sameSite` | `'lax'` または `'strict'` を推奨（CSRF対策と兼ねる） |
| `credentials: 'include'`（フロント） | `fetch` の場合は明示しなくても同一オリジンとして動作するため不要。ただし明示しても問題ない |

> **本番環境での画面配信方法（■要確認）：**
> 本番では Vite の `npm run build` で生成した静的ファイルを **Express から配信する**（`express.static`）か、**別のホスティング（Nginx、S3、Vercel 等）に置いてExpress API だけ別ホストで動かす**か、どちらも選択肢として考えられます。本番用のデプロイ構成はチームで確認してください。

**何をする機能か：** ユーザーが日本語（または英語）で商品の特徴を入力する窓口です。英語のキーワードを知らなくても使えます。

- **入力：** テキストボックスへの任意の文字列
- **出力：** 後続処理（FR-02〜FR-05）の起動

**【現状との差異 D-01】** 入力が空の場合にバリデーションメッセージを表示する仕様は要件定義書に記載がなく、現状も実装されていない（何も起きない）。移行後も同様の挙動とするか■要確認。

const [keyword, setKeyword] = useState<string>('');

const handleSearch = async () => {

### FR-02：意図判定・キーワード抽出

**何をする機能か：** Claude AIが「今すぐ買いたい」なのか「相場を知りたい」なのかを判断し、最初に表示するタブを自動選択します。FR-03・FR-08と1回のAPI呼び出しにまとめて実装されています。

#### 現状（JavaScript）の実装

**バックエンド（`src/index.js`）：**

```
POST /api/smart-search を受信
    │
    ├── DEV_MOCK=1 → ダミーデータを返す（Claude APIを呼ばない）
    ├── キャッシュヒット → 保存済みの結果を返す
    └── キャッシュなし
          │
          ▼
    scopeInstruction（検索範囲の指示文）を組み立てる
          │
          ▼
    Claude API に以下を含むプロンプトを送信:
      ・ユーザーの入力テキスト
      ・検索範囲の指示（domestic / overseas / global）
      ・信頼性判定の基準（trusted / unknown / risky の説明）
      ・返答形式（JSON のみで返すよう指示）
          │
          ▼
    返答テキストから JSON を正規表現で抽出:
      textBlock.text.match(/\{[\s\S]*\}/)
          │
          ├── JSON抽出失敗 → throw Error → HTTP 500
          └── 成功 → JSON.parse() してキャッシュに保存してから返す
```

**intent（意図）の値と意味：**

| 値 | 意味 | 最初に選ばれるタブ |
|---|---|---|
| `current` | 今すぐ買いたい | 現行販売タブ |
| `auction` | 相場を知りたい・過去の取引を調べたい | 過去の相場タブ |
| `unknown` | どちらか不明 | 現行販売タブ（デフォルト） |

- **入力：** `{ text: string, scope: string }` （POST ボディ）
- **出力：** `{ keyword, intent, results, cached?, mock? }` のJSON
- **エラー時：** HTTP 500 `{ error: '検索に失敗しました' }` を返す。フロントエンドでは `smartError = true` にして「検索に失敗しました。」を表示する

#### 移行後（React）の設計案

```typescript
// SearchPage.tsx
const [intent, setIntent] = useState<'current' | 'auction' | 'unknown'>('unknown');

// API呼び出し後
const result = await smartSearch(keyword, scope);
setIntent(result.intent ?? 'unknown');

// 意図に応じてタブを自動選択（FR-05と連動）
useEffect(() => {
  setActiveTab(intent === 'auction' ? 'auction' : 'current');
}, [intent]);
```

### FR-03：現行販売サイト一覧表示

**何をする機能か：** Claude AIが実際にWeb検索を行い、その商品を今購入できるサイトを6〜10件程度探して一覧で返します。固定のリストではなく毎回動的に検索するため、新しいサイトも拾えます。

#### 現状（JavaScript）の実装

FR-02と同じ `/api/smart-search` エンドポイントで処理されます（1回のAPI呼び出しで意図判定・検索・信頼性判定をまとめて実施）。

**フロントエンドの描画（`search.html` `renderResults()` 関数）：**

```javascript
// smartItems（グローバル変数）に格納された結果を使って描画する
const visible = smartItems.filter(item => matchesFilter(item.region === 'overseas'));
visible.forEach(item => {
  // カードのHTML文字列を生成して appendChild する
  // XSSを防ぐため、すべてのテキストを esc() でエスケープしてから出力する
});
```

> **XSS（クロスサイトスクリプティング）とは：**
> 検索結果のタイトルに `<script>alert('攻撃')</script>` のような文字列が含まれていた場合、そのまま画面に出力するとスクリプトが実行されてしまう攻撃です。
> `esc()` 関数で `<` を `&lt;` に変換するなど、無害な文字列に置き換えることで防いでいます。
> Reactでは `{変数}` の形で書くと自動的にエスケープされるため、`esc()` 相当の処理は不要になります。

**各カードに表示される情報：**

| 表示内容 | レスポンスのキー | 補足 |
|---|---|---|
| サイト名・商品名 | `title` | リンクのテキスト |
| URL | `url` | 外部リンク（別タブで開く） |
| 簡単な説明 | `snippet` | Claudeが自分の言葉で書いた説明 |
| 信頼性バッジ | `trust` | trusted / unknown / risky（FR-08） |
| 地域バッジ | `region` | overseas の場合「海外サイト」と表示 |
| ハートボタン | — | お気に入り登録（FR-10） |

- **エラー時：** `smartError = true` になり「検索に失敗しました。」を表示
- **0件時：** 「該当するサイトはありません。」を表示

### FR-08：サイトの信頼性判定・バッジ表示

**何をする機能か：** 検索結果の各サイトに「信頼できる」「情報不足」「危険の可能性」の3段階バッジを付けます。2段階の判定（AI + 客観指標）を組み合わせています。

#### 現状（JavaScript）の実装

**第1段階：Claude AIによる判定（`/api/smart-search` 内）**

Claudeへのプロンプトに信頼性判定の基準を含め、各サイトに `trust`（trusted / unknown / risky）と `trustReason`（理由の1文）を付けて返してもらいます。

**第2段階：客観指標による補正（`applyObjectiveIndicators()` 関数）**

AI判定の後に、ドメインの登録日などの客観的な情報でチェックします。

```
各サイトのURLについて analyzeDomain() を呼び出す
    │
    ├── RDAP APIでドメインの登録日を取得する
    │     ※ RDAP = ドメイン情報を公式に問い合わせるAPI
    │     ※ .jp ドメインは取得できないことが多い（要件定義書 FR-08参照）
    │
    ├── 強い指標（1つで risky 確定）:
    │     ドメイン登録から 90日未満
    │
    └── 弱い指標（2つ以上で risky 確定）:
          ドメイン登録から 1年未満（90日以上）
          HTTP 接続（暗号化なし）
          .top .xyz .click などの危険なドメイン種別
          ドメイン名のハイフンが3個以上

→ 強い指標1個 OR 弱い指標2個以上 → trust を "risky" に引き上げ
→ trustAdjusted = true, trustEvidence に根拠を配列で格納
```

**フロントエンドのバッジ表示：**

| trust値 | クラス名 | 表示テキスト |
|---|---|---|
| `trusted` | `trust-trusted` | 信頼できるサイト（緑背景） |
| `unknown` | `trust-unknown` | 情報の少ないサイト（黄背景） |
| `risky` | `trust-risky` | ⚠️信頼性の低いサイトの可能性があります（赤背景） |

### FR-09：アカウント登録・ログイン

**何をする機能か：** メールアドレスとパスワードで会員登録・ログイン・ログアウトができます。パスワードはBCrypt（暗号化の一種）でハッシュ化して保存します。

#### 現状（JavaScript）の実装

**フロントエンド（`login.html`）：**
1つのHTMLファイルで「ログイン」と「新規登録」を切り替えます（`isLoginMode` フラグで制御）。
ログイン成功後は `/search.html` へ遷移（固定）。

**バックエンド（`index.js`）の処理フロー：**

```
POST /api/signup（新規登録）
    ├── email または password が未入力 → 400
    ├── bcrypt.hash(password, 10) でハッシュ化
    ├── INSERT INTO users ... → OK → 200「登録に成功しました」
    └── UNIQUE制約違反 → 400「すでに登録されているメールアドレスです」

POST /api/login
    ├── DB から SELECT WHERE email = ?
    ├── ユーザーが見つからない → 401
    ├── bcrypt.compare(入力パスワード, DBのhash)
    ├── 一致しない → 401「メールアドレスまたはパスワードが違います」
    └── 一致 → req.session.userId = user.id → 200「ログインしました」

POST /api/logout
    └── req.session.destroy() → 200「ログアウトしました」
```

> **BCryptとは：** パスワードを安全に保存するための「一方向ハッシュ関数」の一種です。同じパスワードでも毎回異なるハッシュ値が生成されるため、DBが盗まれてもパスワードを逆算されにくいという特徴があります。`bcrypt.hash(password, 10)` の `10` はハッシュ計算の複雑さ（ラウンド数）で、大きいほど安全ですが計算時間も増えます。

**セッション管理：**
- `express-session` でサーバーサイドのセッションを使用します
- ログイン後は `req.session.userId` にユーザーIDを保存します
- **【現状との差異 D-05】** セッションの秘密鍵（`secret`）が `'kari-no-himitsu-kagi'` とソースコードに直書きされています。GitHubに公開するとセキュリティリスクになります。早急に環境変数（`.env`）へ移動することを強く推奨します

### FR-13：検索範囲切り替え（国内/国内外/国外）

**何をする機能か：** 検索結果を「国内外（すべて）」「国内のみ」「国外のみ」で絞り込みます。1回の検索で全結果を取得し、フロントエンド側で表示を絞り込みます。

#### 現状（JavaScript）の実装

**フロントエンド（`search.html`）：**

```javascript
let regionFilter = 'all'; // 'all' | 'domestic' | 'overseas'

// フィルタ関数（renderResults から呼ばれる）
function matchesFilter(isOverseas) {
  if (regionFilter === 'all') return true;
  return regionFilter === 'overseas' ? isOverseas : !isOverseas;
}

// 過去相場リンクの絞り込み（海外サイトの定義）
const OVERSEAS_SITE_KEYS = ['ebaySold', 'etsy', 'aliexpress'];
// domestic 時: これらを除外 / overseas 時: これらのみ表示
```

**バックエンド（`src/index.js`）：**
- `normalizeScope()` 関数で `scope` の値を `'domestic' | 'global' | 'overseas'` に正規化
- Claude APIへの指示文（`scopeInstruction`）が scope に応じて変わる
- Claudeの返答に scope と矛盾する地域のサイトが混入していた場合は、安全策として除外する

**キャッシュキーに scope が含まれる：**

```
"smart|global|ナイキスニーカー"   ← 国内外検索
"smart|domestic|ナイキスニーカー" ← 国内検索
"smart|overseas|ナイキスニーカー" ← 国外検索
```
同じキーワードでも scope が違えば別々のキャッシュになります。

## 6. データ設計の詳細

### 6.1 データベースの概要

| 項目 | 内容 |
|---|---|
| DBエンジン | SQLite（`better-sqlite3` ライブラリを使用） |
| DBファイル | `src/app.db`（Gitで管理しない。`.gitignore` に記載） |
| 初期化 | `src/db.js` の `db.exec()` で起動時に `CREATE TABLE IF NOT EXISTS` を実行 |
| ORMの有無 | なし（SQL文を直接書いている） |

> **SQLiteとは：** 1つのファイル（`app.db`）にすべてのデータを保存するシンプルなデータベースです。小規模なアプリケーションや開発・デモ用途に向いています。サーバーを別途起動する必要がないため、セットアップが簡単です。

### 6.2 usersテーブル

```sql
CREATE TABLE IF NOT EXISTS users (
  id            INTEGER  PRIMARY KEY AUTOINCREMENT,
  email         TEXT     UNIQUE NOT NULL,
  password_hash TEXT     NOT NULL,
  created_at    DATETIME DEFAULT CURRENT_TIMESTAMP
);
```

| カラム名 | 型 | 制約 | 説明 |
|---|---|---|---|
| id | INTEGER | 主キー、自動採番 | ユーザーID（内部管理用） |
| email | TEXT | UNIQUE（重複不可）、NOT NULL | メールアドレス（ログインID） |
| password_hash | TEXT | NOT NULL | BCryptでハッシュ化されたパスワード（`$2b$` で始まる文字列） |
| created_at | DATETIME | デフォルト: 現在日時 | 登録日時 |

**注意事項：**
- `email` に UNIQUE 制約があるため、重複登録時は SQLite の例外が発生します。バックエンドでこれをキャッチして 400 を返しています
- メールアドレスの大文字・小文字の正規化（`user@example.com` と `USER@EXAMPLE.COM` を同一とみなす）は実装されていません（■要確認）

### 6.3 favoritesテーブル

```sql
CREATE TABLE IF NOT EXISTS favorites (
  id          INTEGER  PRIMARY KEY AUTOINCREMENT,
  user_id     INTEGER  NOT NULL,
  keyword     TEXT     NOT NULL,
  url         TEXT     NOT NULL,
  site_name   TEXT,
  created_at  DATETIME DEFAULT CURRENT_TIMESTAMP,
  FOREIGN KEY (user_id) REFERENCES users(id),
  UNIQUE (user_id, url)
);
```

| カラム名 | 型 | 制約 | 説明 |
|---|---|---|---|
| id | INTEGER | 主キー、自動採番 | お気に入りID |
| user_id | INTEGER | NOT NULL、外部キー → users.id | 誰のお気に入りか |
| keyword | TEXT | NOT NULL | 登録時の検索キーワード（画面表示用） |
| url | TEXT | NOT NULL | お気に入りURL |
| site_name | TEXT | NULL可 | サイト名（画面表示用） |
| created_at | DATETIME | デフォルト: 現在日時 | 登録日時 |

**複合ユニーク制約：** `(user_id, url)` の組み合わせが重複不可。同じユーザーが同じURLを2回登録しようとすると `UNIQUE constraint failed` エラーが発生します。これをバックエンドで 409 に変換しています。

**外部キー制約の注意：** `FOREIGN KEY` は SQLite では明示的に有効化しないと機能しません。現状の `db.js` には `PRAGMA foreign_keys = ON;` が書かれていないため、外部キー制約は実質的に無効です（■要確認：移行時に追加するか）。

### 6.4 サーバー内キャッシュの仕様

> キャッシュはサーバーのメモリ上に保存されます。DBには保存されないため、**サーバーを再起動するとキャッシュは消えます。**

**実装場所：** `src/index.js` のモジュールスコープ変数

```javascript
const responseCache = new Map(); // キャッシュの実体（キー → 値のペア）
const CACHE_LIMIT = 200;         // 最大保持件数
```

**キャッシュキーの形式：**

| 用途 | キー形式 | 例 |
|---|---|---|
| スマート検索 | `"smart\|{scope}\|{キーワード（小文字）}"` | `"smart\|global\|ナイキスニーカー"` |
| 相場チェック | `"market\|\|{キーワード（小文字）}"` | `"market\|\|遊戯王 青眼の白龍"` |

> キーワードを小文字に変換（`.toLowerCase()`）してからキーにするため、「ナイキ」と「NAIKI」は別キャッシュになります（■要確認：大文字小文字を同一視すべきか）。

**有効期限の管理：**

```javascript
function cacheGet(key) {
  if (CACHE_MINUTES <= 0) return null; // CACHE_MINUTES=0 で無効化
  const entry = responseCache.get(key);
  if (!entry) return null;
  // 保存時刻から経過した時間を計算
  if (Date.now() - entry.savedAt > CACHE_MINUTES * 60 * 1000) {
    responseCache.delete(key); // 期限切れを削除
    return null;
  }
  return entry.value;
}
```

**上限超過時の挙動：**
200件を超えた場合、`responseCache.keys().next().value`（最初に追加されたキー）を削除します。
これは厳密な LRU（最近使われていないものから削除）ではありません。

**環境変数による制御（`src/index.js` で読み込み）：**

| 環境変数名 | デフォルト値 | 説明 |
|---|---|---|
| `CLAUDE_MODEL` | `'claude-sonnet-4-6'` | 使用するClaude AIのモデル名 |
| `DEV_MOCK` | `'0'`（無効） | `'1'` にするとAPIを呼ばずダミーデータを返す |
| `CACHE_MINUTES` | `60` | キャッシュの有効期間（分）。`0` でキャッシュ無効 |
| `WEB_SEARCH_MAX_USES` | `3` | 1リクエストあたりのWeb検索回数の上限 |
| `ANTHROPIC_API_KEY` | なし（必須） | Claude APIのキー（`.env`に記載） |

## 8. 状態管理の設計

### 8.1 採用方針

**ログイン状態（`/api/me` の結果）だけを React Context で共有し、それ以外の状態は各画面の `useState` で管理します。**

ルーティングは **React Router v6** を使います。これらはあくまで「案として採用」した方針です。画面数や機能が大幅に増えた場合は Zustand 等の外部ライブラリへの切り替えも選択肢になります。

### 8.2 現状のグローバル変数とReact Stateの対応

現在の `search.html` は、ファイル全体から参照できる変数（グローバル変数）でアプリの状態を管理しています。
これをReactに移行する際には、各変数をどのコンポーネントの State に置くかを決める必要があります。

| 現状のグローバル変数 | 型 | 役割 | 移行後の置き場所 |
|---|---|---|---|
| `regionFilter` | `string` | 国内/国外フィルタの選択状態 | `SearchPage` の `useState` |
| `smartItems` | `array` | スマート検索の結果リスト | `SearchPage` の `useState` |
| `smartError` | `boolean` | スマート検索のエラー状態 | `SearchPage` の `useState` |
| `auctionUrls` | `object` | 過去相場リンクのURLオブジェクト | `SearchPage` の `useState` |
| `lastKeyword` | `string` | 直前の検索キーワード（お気に入り登録に使う） | `SearchPage` の `useState` |
| `favoritedUrls` | `Set` | 登録済みURLの集合（ハートの状態管理） | `SearchPage` の `useState` |
| `isLoginMode` （login.html） | `boolean` | ログイン/新規登録モードの切り替え | `LoginPage` の `useState` |

これらはすべて特定の画面だけで使うデータなので、**グローバルな状態管理は不要で `useState` で十分**です。

### 8.3 ログイン状態の管理（AuthContext）

ログイン状態だけは Nav・SearchPage・MyPage など複数の画面から参照するため、**React Context API でアプリ全体に共有します。**

> **React Context（コンテキスト）とは：** Reactが持つ「アプリ全体で共有したいデータを渡す仕組み」です。ログイン状態のようなデータを、各コンポーネントにpropsで1つずつ渡す手間なく使えます。

**仕組みの概要：**

```
App.tsx
  └── <AuthProvider>          ← アプリ全体を囲む
        ├── Nav.tsx            ← useAuth() でログイン状態を参照
        ├── SearchPage.tsx     ← useAuth() でお気に入りボタンの制御に使う
        ├── MyPage.tsx         ← useAuth() で未ログイン時はリダイレクト
        └── LoginPage.tsx      ← useAuth() のcheckAuth() をログイン後に呼ぶ
```

**実装案（`frontend/src/hooks/useAuth.ts`）：**

```typescript
import { createContext, useContext, useEffect, useState } from 'react';
import { getMe, logout } from '../services/api';

interface AuthState {
  isLoggedIn: boolean;
  userId: number | null;
  checkAuth: () => Promise<void>;    // ログイン状態を再確認する
  handleLogout: () => Promise<void>; // ログアウト処理
}

const AuthContext = createContext<AuthState | null>(null);

// アプリ全体を AuthProvider で囲む（App.tsx に書く）
export const AuthProvider: React.FC<{ children: React.ReactNode }> = ({ children }) => {
  const [userId, setUserId] = useState<number | null>(null);

  const checkAuth = async () => {
    const me = await getMe(); // /api/me を呼ぶ
    setUserId(me?.userId ?? null);
  };

  const handleLogout = async () => {
    await logout(); // /api/logout を呼ぶ
    setUserId(null);
  };

  useEffect(() => { checkAuth(); }, []); // アプリ起動時に一度だけ確認

  return (
    <AuthContext.Provider value={{ isLoggedIn: userId !== null, userId, checkAuth, handleLogout }}>
      {children}
    </AuthContext.Provider>
  );
};

// 各コンポーネントでの使い方
export const useAuth = () => {
  const ctx = useContext(AuthContext);
  if (!ctx) throw new Error('AuthProvider の中で使ってください');
  return ctx;
};
```

```typescript
// Nav.tsx での使い方例
const { isLoggedIn, handleLogout } = useAuth();
```

**この方針のポイント：**

- `/api/me` の呼び出しはアプリ起動時の **1回だけ**（ページ遷移のたびに呼ばない）
- ログイン・ログアウト後は `checkAuth()` / `handleLogout()` を呼んで状態を更新する
- Context に入れるのはログイン状態のみ。検索結果やフィルタは各ページの `useState` で持つ

### 問題①：セッションの秘密鍵がハードコード（D-05）

**現状のコード（`src/index.js` 27行目）：**

```javascript
app.use(session({
  secret: 'kari-no-himitsu-kagi', // ← ソースコードに直書きされている
  resave: false,
  saveUninitialized: false
}));
```

**リスク：** この文字列がGitHubなどに公開されると、攻撃者がセッションCookieを偽造できる可能性があります。

**対応手順：**

```bash

node -e "console.log(require('crypto').randomBytes(64).toString('hex'))"
# 出力例: a3f8c2d1e9b7... (128文字の16進数)

# 2. src/.env に追記する（.env は .gitignore で Git 管理対象外になっている）
SESSION_SECRET=a3f8c2d1e9b7... （上で生成した文字列）
```

```javascript
// 3. index.js を修正する
app.use(session({
  secret: process.env.SESSION_SECRET || 'dev-only-fallback',
  // ↑ 環境変数がない場合（ローカル開発時）のフォールバックとして別の文字列を設定
  resave: false,
  saveUninitialized: false,
  cookie: {
    httpOnly: true,   // JavaScript からCookieを読めないようにする（XSS対策）
    sameSite: 'lax',  // CSRF対策（後述）
    secure: process.env.NODE_ENV === 'production' // 本番では HTTPS のみ
  }
}));
```

### 問題②：CSRF対策が未実装

> **CSRF（クロスサイトリクエストフォージェリ）とは：** ログイン済みユーザーを罠のサイトへ誘導し、ユーザーが意図しないAPIリクエスト（例：お気に入り全削除）を本サービスへ勝手に送らせる攻撃です。

**現状：** `POST /api/favorites` や `POST /api/login` 等に CSRF 対策がありません。

**対応方法の選択肢（■要確認）：**

#### 選択肢A：SameSite Cookie を設定する（最も簡単）

```javascript
// 上記のセッション設定に sameSite を追加するだけでよい
cookie: {
  sameSite: 'lax', // または 'strict'
  // 'lax': 同じサイトからのリクエストのみCookieを送る（一般的な設定）
  // 'strict': さらに厳しい（リンクからのアクセスでもCookieを送らない）
}
```

| メリット | デメリット |
|---|---|
| コード変更が最小限 | 古いブラウザで動作しない場合がある（まれ） |
| ライブラリ追加不要 | |

#### 選択肢B：CSRFトークンを使う（より確実）

> **CSRFトークンとは：** サーバーがランダムな文字列（トークン）を発行し、フォームや API リクエストに含めることを要求する仕組みです。悪意のあるサイトはこのトークンを知ることができないため、不正なリクエストを防げます。

```bash
# csrf パッケージの代替として、csurf の後継である csrf-csrf を使う場合
npm install csrf-csrf
```

```javascript
const { doubleCsrf } = require('csrf-csrf');
const { generateToken, doubleCsrfProtection } = doubleCsrf({ getSecret: () => process.env.SESSION_SECRET });

app.use(doubleCsrfProtection); // POST等に自動でチェックが入る

// トークン取得エンドポイント（フロントエンドが最初に呼ぶ）
app.get('/api/csrf-token', (req, res) => {
  res.json({ token: generateToken(req, res) });
});
```

| メリット | デメリット |
|---|---|
| より確実な CSRF 対策 | フロントエンドの変更も必要（すべてのPOSTにトークンを付ける） |
| | ライブラリの追加が必要 |

**卒論規模での推奨：** `SameSite: 'lax'`（選択肢A）を設定するだけで、一般的な CSRF 攻撃には十分な対策になります。選択肢Bはより本格的な対策ですが、実装コストが高いため、余裕があれば追加してください。
