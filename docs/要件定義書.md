## 2. システム概要

### 2.1 背景

- 海外にしか流通していない商品(限定品・未発売品)に興味があっても、探す手段が限られている
- 既存の輸入代行・転送サービス(Buyee、malltail、Shipito等)は「購入後」の物流支援が中心であり、「そもそも何がどこで買えるか」を発見する支援が手薄
- 海外通販の利用経験において、以下のような障壁が実際に確認されている
  - 検索キーワードが分からない(英語の壁)
  - 決済・関税の仕組みが分かりにくい
  - 商品ページを開くまで「日本への発送に対応しているか」が分からず、購入直前で離脱するケースがある(実体験:eBay利用時)
  - 検索結果に表示されるサイトの中には信頼性の低いもの(詐欺的なサイト)も混在しており、検索エンジンに表示されること自体が安全性を保証しない(実体験:某通販サイト「Oショップ」)

### 2.2 目的

自然言語による入力から、国内外の「現在購入できるサイト」および「過去の取引実績(オークション等)」への案内を横断的に提示することで、越境ECにおける商品発見のハードルを下げる。

### 2.3 スコープ

**対象範囲**
- 商品名・特徴を自然言語で入力すると、関連する外部ECサイト・オークションサイトの検索結果URLを一覧表示する
- 決済方法・関税・用語解説などのヘルプコンテンツを提供する
- Webサイト版に加え、Chrome拡張機能から閲覧中ページを比較する導線を提供する

**対象外(本サービスでは扱わない)**
- 商品の購入・決済処理そのもの(あくまで外部サイトへの案内に徹する)
- 商品データ(画像・詳細説明)の自社保存・複製
- 出品者情報や在庫状況など、外部サイトから詳細データを取得・自社表示する機能

### 2.4 想定ユーザー

- 海外限定品・未発売品に関心があるが、英語や海外通販の仕組みに不慣れな一般ユーザー
- 海外オークションでの過去の取引相場を知りたいユーザー

## 3. 要求獲得プロセス

REBOK(要求工学知識体系)の考え方に基づき、本要求がどのように獲得されたかを以下に整理する。

| 手法 | 内容 |
|---|---|
| 自己エスノグラフィ(実体験の洗い出し) | チームメンバー自身の海外通販利用経験(eBayでの発送非対応、詐欺サイトへの遭遇等)を要求の出発点とした |
| 既存サービス調査 | 輸入代行・転送サービス(Buyee等)を調査し、「発見」を支援する機能が手薄であることを課題として特定した |
| 有識者・指導教員へのヒアリング | 指導教員からのアドバイスにより、ビジネス面の弱さを補うためChrome拡張機能(FR-11)としての展開を検討課題に追加した |

## 4. 用語定義

| 用語 | 定義 |
|---|---|
| 現行販売サイト | 現在その商品を購入可能なECサイト(Amazon、eBay即決、Etsy等) |
| 過去のオークション履歴 | 落札済み(Sold)商品の情報が見られる検索結果ページ(eBay Sold、ヤフオク!等) |
| URLテンプレート方式 | 各サイトの検索URLの型にキーワードを差し込んでURLを自動生成する方式 |
| 意図判定 | ユーザー入力から「今すぐ購入したい」/「相場を知りたい」等の意図をLLMが推定する処理 |

## 5. 機能要件

優先度はMoSCoW法(Must:必須/Should:重要/Could:可能なら/Won't:今回対象外)で示す。実装状況は2026年9月14日時点。

### FR-01 自然言語検索

- ユーザーはテキストボックスに自由記述で商品の特徴・名称を入力できる
- 入力例:「軽くて防水のトレッキングシューズ、海外限定モデル」
- **優先度**: Must
- **根拠**: 英語や専門的な検索キーワードが分からず、海外通販の利用に心理的ハードルを感じていた実体験に基づく(2.1)
- **実装状況**: ✅ 実装済み。テキスト入力から、FR-02(意図判定)を経由してFR-03/FR-04両方の検索が行われる

### FR-02 意図判定・キーワード抽出

- LLM(Claude API)を用いて、入力文から検索キーワードと意図(現行購入/相場確認/不明)を抽出する
- 意図が不明瞭な場合は両方の検索結果を提示する
- **優先度**: Must
- **根拠**: 「今すぐ買いたい」のか「相場を知りたい」のかで求める情報が異なるため、ユーザーの曖昧な入力から適切に振り分ける必要がある
- **実装状況**: ✅ 実装済み。FR-03・FR-08と統合したAPI(`/api/smart-search`)として、Claude API 1回の呼び出しでキーワード抽出・意図判定・Web検索・信頼性判定をまとめて実施する設計に変更

### FR-03 現行販売サイトへの案内

- Web検索を用いて、抽出したキーワードで現行販売サイトを検索する
- 商品名・簡易説明(自分の言葉での要約)・URLをカード形式で一覧表示する
- コードに固定のドメインリストを持たず、検索時点で実在するサイトを動的に取得する
- **優先度**: Must
- **根拠**: 国内外を横断して「今どこで買えるか」を一度に確認できるサービスが少ないという課題に基づく(2.1)
- **実装状況**: ✅ 実装済み(設計変更あり)。当初想定していたGoogle Custom Search JSON APIは、2027年1月1日までに新規顧客への提供を終了する方針であることが判明し、新規開発では利用不可であることを複数のGoogle Cloudプロジェクトで確認した。代替として、Claude APIのWeb検索ツール(`web_search_20250305`)を採用し、FR-02・FR-08と統合した`/api/smart-search`エンドポイントとして実装した。この方式により、固定ドメインリストに縛られず任意の実在サイトを動的に検索結果へ含められる利点が得られた

### FR-04 過去のオークション/相場サイトへの案内

- あらかじめ定義したオークション・フリマサイトの検索URLテンプレートに、キーワードを差し込んでURLを生成する
- 対象サイト:ヤフオク!、eBay(Sold Listings絞り込み)、メルカリ、Amazon、楽天市場
- 実データの取得・保存は行わない(URL生成のみ)
- **優先度**: Must
- **根拠**: 相場を知る手段が個別サイトの検索に限られており、横断的に確認できないという課題に基づく
- **実装状況**: ✅ 実装済み

### FR-05 検索結果の表示切り替え

- 「現行販売」タブと「過去の相場」タブを切り替えて表示できる
- 意図判定の結果に応じて、初期表示するタブを自動選択する
- **優先度**: Should
- **根拠**: FR-02の意図判定結果をユーザーに分かりやすく提示するために必要
- **実装状況**: ❌ 未実装(FR-02未実装のため保留)

### FR-06 為替換算の目安表示

- 為替レートAPIを用いて、米ドル-円の参考レートを表示する
- 「送料・関税別、参考価格」である旨を明記する
- **優先度**: Should
- **根拠**: 現地通貨表示のみでは実質的な価格が分かりにくく、購入判断がしづらいという課題に基づく
- **実装状況**: ✅ 実装済み(exchangerate-api.comを使用、検索画面に表示)

### FR-07 ヘルプコンテンツ

- 以下の内容を静的コンテンツ(自作の解説文)として提供する
  - 決済方法の解説(クレジットカード、PayPal、Wise等)
  - 関税・消費税の仕組み
  - 頻出英単語辞典(Buy It Now、Bid 等)
  - 転送サービスの説明とリンク集
  - 怪しいサイトの見分け方(価格が相場より極端に安い、支払い方法が銀行振込のみ、不自然な日本語、ドメイン取得が新しい、会社情報が不明瞭、レビューが不自然、なりすましドメイン、SSLの過信に対する注意 等)
- **優先度**: Should
- **根拠**: 決済・関税の仕組みが分からず不安を感じた実体験、および詐欺サイトの見分け方を知らなかったために某通販サイト(Oショップ)に騙されかけた実体験に基づく(2.1)
- **実装状況**: ✅ 実装済み(目次からのページ内ジャンプ付き)

### FR-08 サイトの信頼性判定・表示

- 検索結果として表示する各サイトについて、信頼性を3段階(trusted:信頼できる/unknown:情報の少ないサイト/risky:信頼性の低いサイトの可能性)で判定し、バッジ形式で表示する
- 判定基準:ブランド公式サイト・大手ECサイトは"trusted"、実在するが小規模・聞き馴染みのないサイトは"unknown"、ドメインが不自然・詐欺的特徴が見られるサイトは"risky"
- **優先度**: Should
- **根拠**: 検索結果に表示されること自体が安全性の保証にならないという実体験(某通販サイト「Oショップ」等)に基づく(2.1)
- **実装状況**: ✅ 実装済み(設計変更あり)。当初想定していたGoogle Safe Browsing APIは`API_KEY_SERVICE_BLOCKED`エラーが解消できなかったため、Claude APIによる検索結果への同時判定方式に変更した。FR-03の検索と同一のAPI呼び出し内で、各サイトの信頼度をClaude自身に判定させる設計とした。外部の専門機関によるブラックリスト照合ではなく、LLMによる推論ベースの簡易判定である点は限界として認識しておく必要がある

### FR-09 アカウント登録・ログイン機能

- メールアドレス・パスワードによる新規登録、ログイン、ログアウトができる
- パスワードはハッシュ化して保存し、平文では保存しない
- **優先度**: Could
- **根拠**: FR-10(お気に入り登録)を実現するための前提機能。また、卒論としてログイン・データベースを含む一通りの実装を行う目的も兼ねる
- **実装状況**: ✅ 実装済み(Express + bcrypt + express-session)

### FR-10 お気に入り登録機能

- ログイン済みユーザーは、検索結果カードから商品(またはその検索結果URL)をお気に入りとして保存できる
- 保存したお気に入りは、マイページから一覧・削除ができる
- 同一ユーザー・同一URLの重複登録は不可(データベースのUNIQUE制約)
- **優先度**: Could
- **根拠**: 気になった商品を後から見返したいというニーズに基づく。ログイン機能(FR-09)の具体的な活用先として位置づける
- **実装状況**: ✅ 実装済み(ハートマーク♡での登録、マイページでの☓マーク削除)

### FR-11 Chrome拡張機能:閲覧中ページからの比較

- ユーザーが任意のECサイトの商品ページを閲覧中に、拡張機能のアイコンをクリックすると、ポップアップ画面が開く
- ポップアップは、そのページのタイトルを自動でキーワードとして読み取り、FR-04と同じ仕組みで他サイトの検索URLを一覧表示する
- Webサイト版と同じアカウントでログインでき、お気に入り登録(FR-10)も同様に行える
- **優先度**: Should
- **根拠**: 指導教員からのアドバイスに基づく。既存の類似サービス(Honey等)の実績から、閲覧中の比較導線がユーザーの利用頻度・収益化(アフィリエイト)の両面で有利であるため
- **実装状況**: ✅ 実装済み(Manifest V3、Web版とセッション共有)

### FR-12 相場チェック機能

- ユーザーが検索窓に商品名を入力し「相場」ボタンを押すと、その商品の現在の実勢価格帯を調べて表示する
- 入力が「クレヨンしんちゃん」のような作品名・カテゴリ名など曖昧な場合は、「キーワード不足、正式な商品名を入力してください」と表示し、具体的な商品名(型番・年代等を含む)の場合のみ相場を表示する
- 表示内容:発売時期、発売元・メーカー、商品概要(2〜3文)、価格帯(円)
- 価格帯は「一般的な状態」の実勢相場に限定し、鑑定品等による極端な高額事例は価格帯に含めず備考欄で言及するのみとする
- 海外商品の場合、現地通貨(ドル等)の相場を為替レートで円換算して表示する(現地通貨の数値をそのまま円として誤表示しないよう対策済み)
- **優先度**: Could
- **根拠**: 商品の適正な取引価格が分からず、購入・出品時の判断材料が欲しいというニーズに基づく。プレミア価格がついている商品(生産終了品・コレクター需要の高い商品等)にも対応できることを重視
- **実装状況**: ✅ 実装済み(Claude API、Web検索ツール使用)。開発時の課題として、Web検索を伴う処理のため応答に数十秒〜数分を要する場合があり、タイムアウト設定(180秒)と検索回数制限(3回)で対応した。この点はNFR-02(性能)の課題と共通する

## 6. 非機能要件

### NFR-01 権利遵守方針(最重要制約)

- 外部サイトのコンテンツ(画像・文章)は自社サーバーに保存・複製しない
- 外部サイトへは通常のハイパーリンクのみを用い、iframe等での埋め込みは行わない
- スクレイピングによるデータ取得は行わない。データ取得は公式API・検索API経由に限定する
- 商品説明を表示する場合は、検索結果を要約した自分たちの言葉で記述する(元文章の転載・翻訳表示は行わない)
- 非営利・学術目的での運用とする

### NFR-02 性能

- 検索結果表示までの時間:目標は数秒以内としていたが、Claude APIによるWeb検索を伴う`/api/smart-search`は、LLMの推論+検索+複数サイトの信頼性判定を1回のリクエストで行うため、実測で数秒〜十数秒程度を要する
- ■課題として認識: 従来のURLテンプレート方式(FR-04)は即時応答だが、AI検索方式(FR-03・FR-08)は応答速度とのトレードオフが生じている。ユーザビリティテスト(9章)において、この待ち時間が体験に与える影響を検証項目に含める。改善案としては、検索中であることを示すローディング表示の工夫、結果を受け取り次第逐次表示する方式(ストリーミング)への変更などが考えられる

### NFR-03 可用性

- 卒論発表・デモ時に安定して動作すること(常時稼働は必須要件としない)

### NFR-04 セキュリティ

- APIキー等の秘匿情報はソースコードに直接記載せず、環境変数(.env)で管理し、Gitの管理対象外(.gitignore)とする
- パスワードはbcryptでハッシュ化して保存する(平文保存は行わない)
- ログイン状態の管理にはセッション管理の仕組み(express-session)を用いる

## 9. 妥当性確認(検証)方法

REBOKにおける要求の妥当性確認(Validation)に対応する項目。定義した要求が実際にユーザーの課題を解決するかを、以下の方法で検証する。

- **ユーザビリティテスト**: 被験者に商品検索タスクを行わせ、「発見できた商品数」「タスク完了時間」「満足度アンケート」を既存の検索方法(単純キーワード検索)と比較する。あわせて、AI検索(FR-03・FR-08)の応答待ち時間(NFR-02)が体験にどう影響するかも確認する
- **比較実験**: 「意図判定つき横断検索」と「単純キーワード検索」で、発見できる商品の質・多様性を比較する
- ■要実施: ゼミでの中間発表を通じて、指導教員・他ゼミ生からのフィードバックを要求内容の妥当性確認に用いる

## 10. 将来的な収益モデル(参考)

本サービスは卒業論文としては非営利・学術目的で実装するが、企画としての成立性を示すため、実運用を想定した収益モデルの案を以下に示す。

- **アフィリエイトプログラムの活用**: 本サービスは外部ECサイトへのリンク誘導を中核機能としており、各サイトが提供するアフィリエイトプログラム(Amazonアソシエイト、eBayパートナーネットワーク等)に参加することで、リンク経由の購入に対する成果報酬を得るモデルと親和性が高い
- **広告掲載**: 検索画面にダミーの広告枠(実際の広告配信は行わない、デザインのみ)を実装済み。実運用時はGoogle AdSense等の導入を想定するが、審査要件(一定のアクセス実績等)を満たす必要があるため、卒論の段階では見た目のみの実装に留めている
- **Chrome拡張機能による強化**: FR-11により、ユーザーが商品ページを閲覧している購入検討の瞬間に比較導線を提示できるため、Webサイト単体よりアフィリエイト収益化との親和性が高い(Honey等の先行事例を参考)
- **既存の設計方針との整合性**: アフィリエイトリンクは各サイトが公式に許可した仕組みであり、これまでの「URLへの案内に徹する」という権利遵守方針と矛盾しない
- ■要検討: 広告掲載やフリーミアムモデル等、他の収益化手段についても比較検討の余地がある
